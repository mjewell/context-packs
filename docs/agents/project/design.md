# Why context-packs works the way it does

The [README](../../../README.md) covers how to use it. This covers the choices that look like mistakes until you know the reason.

- **Packs are copied into each repo, not linked or loaded by a hook.** Cloud sessions and fresh clones see only what's committed, and Codex can't include another file from `AGENTS.md`. A link into a plugin's install folder would differ by machine and break wherever the plugin isn't installed. A hook would have to be set up for each agent, and would load every doc up front instead of only when a row matches.
- **A header block the tool owns comes before the packs.** It states the one rule every pack relies on: read a doc when its row matches, and change synced content at its source. That way no pack's rules need to repeat it. Each pack's hash covers its own folder under `docs/agents/packs/`, so an edit is traced to one pack.
- **The blocks sit together as one region.** The tool owns everything from the header block to the last pack block. Adding or removing a pack is then an append or a delete, and a new `AGENTS.md` needs only the two empty header-block lines pasted in. Text between the blocks stops the sync rather than being worked around.
- **The blocks are the list of installed packs.** Each start marker records its pack's origin, path and ref, so there's no separate manifest to keep in step with them.
- **Packs are pinned, except a pack in the synced repo itself.** A pack pinned to a commit or tag syncs the same for everyone until someone runs `update`. `update` moves a release tag only to a newer release with the same prefix, so a pack pinned to a version never lands on an unreleased commit by accident. A pack in the synced repo, `from=.`, is read from the working tree instead, because a commit can't pin itself: that's what lets a repo holding a pack resync its own `AGENTS.md` in the commit that changes the pack.
- **A pack in the synced repo is listed where it is, not copied.** A copy would duplicate every doc in the same repo, and editing your own docs would trip the check for synced content edited in place. So its table points at the docs themselves, and it installs every nested pack it has, since choosing among a repo's own docs means nothing. That's what makes it the home for a repo's own context docs: the table is generated from each doc's `when:` line, so there's no hand-written table to keep in step. Only its nested packs' generated indexes go under `docs/agents/packs/<name>/`, so the tool never writes into files people author, and its hash covers its block and those indexes.
- **A folder with a `pack.md` is a pack wherever it sits.** The pack a repo installs has its `pack.md` pasted into `AGENTS.md`. A pack nested inside it gets a row instead, pointing at a generated index that holds its rules and its own table, so a long subtree costs one read only when its row matches, and no one writes an index by hand. A folder without a `pack.md` only groups files: its docs join the nearest pack's table, so arranging files costs no extra read. Any folder with a `pack.md` can also be installed on its own; its front matter describes it as a child, so it's ignored there.
- **Nesting is a hop by default, and `inline: true` opts out.** A hop costs one read when its row matches, while inlining costs context in every session of every repo that installs the pack. `inline` is for a subtree whose rules apply whenever a repo picks it, such as a language's rules: its rules and table follow its parent's, rendered as they would be if it were installed alone.
- **Only a nested pack is optional.** A doc always comes with the pack it's in, so choosing is per subtree, and a single optional doc becomes a folder with a `pack.md`. Picking a nested pack pulls in the packs above it, and `tier: required` means installed whenever its parent is, so a parent is never installed without docs its rules may rely on.
- **The start marker records the picks.** An inline pack holding only rules writes no file of its own, so which packs a repo picked can't be read back from the synced folder.
- **Every doc needs `when:`, and front matter takes no unknown keys.** A doc without a row would be unreachable, and a key an older version doesn't know, like `inline`, would otherwise be ignored without a word. A way to leave a doc out of the table can come when a pack needs one.
- **Installs from one origin can't overlap.** A pack and a folder inside it from the same origin would sync the inner rules twice, possibly pinned to different refs, so the sync stops. Origins are compared as written: the same repo spelled two ways gets past the check.
- **Packs are added and removed explicitly.** Installing a Claude Code plugin doesn't add its pack. That would tie which packs a repo has to one agent's settings, while what the tool writes works for every agent that reads `AGENTS.md`. A trigger for each agent can come later without changing the format.
- **It's Python behind an npm package.** npx is the familiar way to run a tool like this, and Python needs nothing installed beyond what comes with `git` on macOS. The cost is needing both Node and Python; a rewrite in TypeScript would remove the Python requirement if Windows users or contributors need that.

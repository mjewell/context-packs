# Why context-packs works the way it does

The [README](../../../README.md) covers how to use it. This covers the choices that look like mistakes until you know the reason.

- **Packs are copied into each repo, not linked or loaded by a hook.** Cloud sessions and fresh clones see only what's committed, and Codex can't include another file from `AGENTS.md`. A link into a plugin's install folder would differ by machine and break wherever the plugin isn't installed. A hook would have to be set up for each agent, and would load every doc up front instead of only when a row matches.
- **The sync writes whichever instruction file a repo already uses.** Teams differ on `AGENTS.md` versus `CLAUDE.md`, and on how one reaches the other, and that isn't this tool's call. So it syncs the file holding the blocks, and a repo with files but no blocks picks one by pasting the two marker lines into it. Only a repo with neither file gets the recommendation: a new `AGENTS.md` with `CLAUDE.md` linked to it. Blocks in both files stop the sync rather than syncing both, since two copies of the installed packs could drift apart, and a repo that wants both files can have one import the other. It never writes through a symlink, since its target could be anywhere.
- **A header block the tool owns comes before the packs.** It states the one rule every pack relies on: read a doc when its row matches, and change synced content at its source. That way no pack's rules need to repeat it. Each pack's hash covers its own folder under `docs/agents/generated/`, so an edit is traced to one pack.
- **The blocks sit together as one region.** The tool owns everything from the header block to the last pack block. Adding or removing a pack is then an append or a delete, and a new `AGENTS.md` needs only the two empty header-block lines pasted in. Text between the blocks stops the sync rather than being worked around.
- **The blocks are the list of installed packs, and each marker names a folder on disk.** A start marker holds a pack's name and the folder its block renders, and nothing written by hand. A pack from git is an import pack in that folder, which holds its origin, path and ref, so a pin sits in a file in the repo like any other, and a marker means the same thing for every pack: render the pack in this folder. A marker whose folder is gone stops the sync, saying to fix its `path=` or remove it, and `remove` deletes only the import pack its marker names, never a pack with that name elsewhere, so removing the block of a pack moved into another keeps the pack where it was moved.
- **Packs are pinned, except a pack in a folder on disk.** A pack pinned to a commit or tag syncs the same for everyone until someone runs `update`. `update` moves a release tag only to a newer release with the same prefix, so a pack pinned to a version never lands on an unreleased commit by accident. A pack in a folder of the synced repo is read from the working tree instead, because a commit can't pin itself: that's what lets a repo holding a pack resync its own `AGENTS.md` in the commit that changes the pack. A folder beside the repo, such as `../agent-config/packs/core`, is read the same way, so an author can try a pack in another repo before pushing it, the way `file:` dependencies work in `package.json`. It syncs only where that folder exists, so it's for trying a pack out, not for a repo that clones, CI and cloud sessions sync. An origin is a folder on disk unless it's a git URL, told apart the way git does it, so `.`, the folders beside it and absolute paths follow one rule, and a pack meant to be pinned is named by its git URL.
- **A pack in a folder on disk is listed where it is, not copied.** For a pack in the synced repo, a copy would duplicate every doc in the same repo, and editing your own docs would trip the check for synced content edited in place. So its table points at the docs themselves, and a folder beside the repo gets the same treatment, so editing one of its docs needs no resync either. Listing in place is what makes a folder in the repo the home for its own context docs: the table is generated from each doc's `when:` line, so there's no hand-written table to keep in step. Only its nested packs' generated indexes go under `docs/agents/generated/<name>/`, so the tool never writes into the pack's folder, apart from the pins of the import packs it holds, and its hash covers its block and those indexes.
- **A folder with a `pack.md` is a pack wherever it sits.** The pack a repo installs usually has its `pack.md` pasted into `AGENTS.md`. A pack nested inside it gets a row instead, pointing at a generated index that holds its rules and its own table, so a long subtree costs one read only when its row matches, and no one writes an index by hand. A folder without a `pack.md` only groups files: its docs join the nearest pack's table, so arranging files costs no extra read. Any folder with a `pack.md` can also be installed on its own, and it renders the way it would inside its parent: one with a `when` gets a one-row table in its block, pointing at its index at `docs/agents/generated/<name>/pack.md`, so installing just a language's pack still loads its rules only when they matter. That's its author's suggestion, which the import pack of a repo installing it can overrule.
- **A pack with a `when` is a hop, unless its `when` is `always`.** A hop costs one read when its row matches, while pasting a pack in costs context in every session of every repo that installs it, so a nested pack says which it is with a `when`, and gets a row unless that's `always`. The pack a marker names is also pasted when it has no `when`, the usual case for a repo's own docs and for a pack written to be installed on its own. `always` is a value of `when` rather than a key of its own, so one key decides how every pack loads, a pack you write and an import pack alike, and no two keys can contradict each other. The cost is that no row can read just "always", which no `when` seems to need.
- **A pack installs everything in its folder.** Choosing parts of a pack took a list of picks in each marker, a command to change it, and rules for which packs a pick pulls in, all so an author could nest what is really a pack of its own. A part only some repos want goes in a folder beside its parent's, which those repos install with `add`, and a nested pack is only for putting a big subtree's table behind one row. A pack stands on its own: when its rules rely on another pack's, that pack belongs inside it, so packs never depend on each other and need no way to say so.
- **A pack from git is installed as an import pack, which decides how it loads.** How a pack renders is decided by its root's front matter, so an import pack is a folder the repo owns whose `pack.md` supplies that front matter, while its content comes from the pack it names. Without a `when`, it follows the root `when` of the pack it names, at the import pack's ref: its author's suggestion holds, and moves with `update`. `when:` replaces it with the repo's own, and `when: always` pastes the pack in even when its author gave it a `when`. The author's `when` isn't copied into the import pack, since a copy would be a second source of truth for `update` to keep in step. Every pack from git gets an import pack, even one that overrides nothing, so a repo changes how any pack loads the same way wherever it sits. A marker can name it, by default at `docs/agents/<name>/`, and it gets a block. Or it can sit inside a pack the repo writes, where it renders as that pack's nested pack: a row in its table, or its rules and table pasted after that pack's, so a repo can put several packs behind one row of its own and write rules beside them. Packs nested inside the imported one still render as their author wrote them, until someone needs to change those too.
- **An import pack is a folder holding a `pack.md`, not any file with `from:`.** Every pack being a `pack.md` keeps one rule for finding packs, and a doc's front matter keeps one meaning. The CLI writes the folder, so the extra level costs nothing. The folder holds only `pack.md`, since the repo's own docs beside imported ones would blur which are synced; they can go beside it.
- **Only a pack in a folder on disk can hold import packs.** A fetched pack importing others would bring transitive pins, the same pack imported twice at two refs, names colliding between authors, and cycles. So a fetched `pack.md` with `from:` stops the sync. Lifting that later needs no change to the format.
- **The CLI writes import packs, and leaves only `when` and the rules to people.** `add` writes `from`, `path` and `ref`, and `when` if asked, `update` rewrites `ref`, and `remove` deletes the folder, so nobody resolves a commit by hand. It's the same arrangement as `AGENTS.md`: a file people edit, where the tool writes only the parts it owns.
- **Pack names are unique across a repo, import packs included.** Commands name an import pack alone. One a marker names writes its docs and indexes to its block's folder, `docs/agents/generated/<name>/`, like any pack. One inside another pack writes them to the generated folder of the pack holding it, under the import pack's path, so that pack's hash covers them and an edit to an imported doc is still caught, the next sync clears them once the import pack is gone, and the check for folders without a block needs no exception. The overlap check covers import packs as well.
- **Old formats aren't migrated.** A pack or marker written for an older version stops the sync as front matter it doesn't know or a marker it can't read, and gets fixed by hand. While there's one consumer, that's cheaper than code that reads every old format, and it keeps nothing old around after it's gone.
- **Every doc needs `when:`, and front matter takes no unknown keys.** A doc without a row would be unreachable, and a key an older version doesn't know would otherwise be ignored without a word. A way to leave a doc out of the table can come when a pack needs one.
- **Installs from one origin can't overlap.** A pack and a folder inside it from the same origin would sync the inner rules twice, possibly pinned to different refs, so the sync stops. That's also why a part a repo chooses sits beside its parent's folder, not inside it. Origins are compared as written: the same repo spelled two ways gets past the check.
- **Packs are added and removed explicitly.** Installing a Claude Code plugin doesn't add its pack. That would tie which packs a repo has to one agent's settings, while what the tool writes works for every agent that reads `AGENTS.md`. A trigger for each agent can come later without changing the format.
- **It's Python behind an npm package.** npx is the familiar way to run a tool like this, and Python needs nothing installed beyond what comes with `git` on macOS. The cost is needing both Node and Python; a rewrite in TypeScript would remove the Python requirement if Windows users or contributors need that.

# Why context-packs works the way it does

The [README](../../README.md) covers how to use it. This covers the choices that look like mistakes until you know the reason.

- **Packs are copied into each repo, not linked or loaded by a hook.** Cloud sessions and fresh clones see only what's committed, and Codex can't include another file from `AGENTS.md`. A link into a plugin's install folder would differ by machine and break wherever the plugin isn't installed. A hook would have to be set up for each agent, and would load every doc up front instead of only when a row matches.
- **The sync writes whichever instruction file a repo already uses.** Teams differ on `AGENTS.md` versus `CLAUDE.md`, and on how one reaches the other, and that isn't this tool's call. So it syncs the file holding the block, and a repo with files but no block picks one by pasting the two marker lines into it. Only a repo with neither file gets the recommendation: a new `AGENTS.md` with `CLAUDE.md` linked to it. A block in both files stops the sync, since two copies of the installed packs could drift apart. It never writes through a symlink, since its target could be anywhere.
- **One fixed folder, `context-packs/`, holds every pack a repo has, and where a pack sits decides where it renders.** The repo's own docs and the import pack of each pack from elsewhere are folders in one tree, so the tree is the only configuration: moving a folder and resyncing moves a pack, with nothing else to keep in step. It isn't configurable, since an import pack holding a path already reaches docs kept anywhere else. It's named for the tool rather than `docs/agents/`, where other tools write files without a `when:` that would stop the sync. The sync writes into `context-packs/gen/` and skips it when reading the tree, which keeps the tables' paths short; so `gen` can't be a pack's id.
- **`AGENTS.md` holds one block, whose markers hold no settings.** The block holds a header stating the one rule every pack relies on, read a doc when its row matches and change synced content at its source, followed by the rendered tree. The header names `context-packs/` in its text, since Claude Code strips HTML comments before an agent reads the file. The markers only show where the block starts and ends and hold its hash, and the comments naming each inlined pack are for people: the sync never reads them, so they can't drift from anything. The hash covers the block and everything in `context-packs/gen/`, so any edit to synced content stops the next sync, which names the block and the folder rather than one pack; `git diff` shows which.
- **`check` renders the whole tree rather than checking the hash.** The hash only catches edits to synced content. A `when:` line, a `pack.md` or a `ref` changed without a resync leaves it matching, so only rendering again shows the block is stale. That's why `check` fetches pinned packs, as a sync does.
- **A pack's id is its folder under `context-packs/`.** It's unique by construction, so no rule about unique names is needed, and `add` puts a pack anywhere in the tree without a flag for where.
- **Packs from git are pinned to a commit or a tag, and `update` moves only a commit.** A pinned pack syncs the same for everyone until someone runs `update`, which moves a commit to the tip of the default branch. A tag is opaque: a pack pinned to one stays there until someone names another with `--ref`, so the tool needs no rules for which tags are releases or how they order, and a pack pinned to a version never lands on an unreleased commit by accident.
- **A pack in a folder on disk isn't pinned, and is listed where it is.** It's read from the working tree because a commit can't pin itself: that's what lets a repo holding a pack resync its own `AGENTS.md` in the commit that changes the pack. Its table points at the docs themselves rather than copies, since a copy would duplicate every doc in the same repo and trip the check for synced content edited in place. That makes `context-packs/` the home for a repo's own docs, with a table generated from their `when:` lines. A folder beside the repo, such as `../agent-config/packs/core`, is read the same way, so an author can try a pack before pushing it, the way `file:` dependencies work in `package.json`; it syncs only where that folder exists, so it isn't for a repo that clones, CI and cloud sessions sync. An origin is a folder on disk unless it's a git URL, told apart the way git does it, so `.`, sibling folders and absolute paths follow one rule.
- **A folder with a `pack.md` is a pack wherever it sits, and a folder without one only groups files.** A nested pack gets a row pointing at a generated index, so a long subtree costs one read only when its row matches, and no one writes an index by hand. A plain folder's docs join the nearest pack's table, so arranging files costs no extra read. `context-packs/` itself is the pack at the top, inlined into `AGENTS.md`, so its `pack.md` takes no front matter. A pack installed on its own renders the way it would inside its parent, so installing just a language's pack still loads its rules only when they matter.
- **`always` is a value of `when`, not a key of its own.** A row costs one read when it matches, while inlining costs context in every session of every repo, so a pack with a `when` gets a row unless that's `always`. One key then decides how every pack loads, a pack you write and an import pack alike, and no two keys can contradict each other. A pack you import with no `when` anywhere is inlined, the usual case for a pack written to be installed on its own. The cost is that no row can read just "always".
- **A pack installs everything in its folder.** Picking parts would need a list of picks, a command to change it, and rules for which packs a pick pulls in. A part only some repos want goes in a folder beside its parent's, which those repos install with `add`.
- **Every pack from elsewhere is installed as an import pack: a folder the repo owns, holding only a `pack.md`.** How a pack renders is decided by its root's front matter, so the import pack supplies that front matter while its content comes from the pack it names. Without a `when`, it follows its author's, at the import pack's ref, so the suggestion moves with `update`; the author's `when` isn't copied in, since a copy would be a second source of truth. A folder on disk gets an import pack too, so every pack is added, moved and overruled the same way. It's a `pack.md` in a folder, not any file with `from:`, so there's one rule for finding packs and a doc's front matter has one meaning. The folder holds nothing else, so the repo's own docs never mix with synced ones. Packs nested inside the imported one render as their author wrote them.
- **`from` names a repo, and `path` a folder in it; without `from`, it's the repo the import pack is in.** One shape covers a pack from git, a checkout beside the repo, and a folder of the same repo, so switching between trying a pack locally and installing it pinned changes only `from`. Keeping the repo apart from the folder lets a pack point at another folder of its own repo and render the same wherever it's installed. A path is relative to the repo's root, so moving an import pack doesn't break it, and it can't leave its repo, since the repo installing a pack can't know what's beside it.
- **A pack from git can only import folders of its own repo.** Importing a pack from git would bring transitive pins and the same pack at two refs, and a folder on disk would mean something different in every repo installing it. A `path` alone brings neither, since it shares the holder's pin.
- **Packs can't overlap, except the same folder imported in two places.** A pack and a folder inside it from the same origin would sync the inner rules twice, so the sync stops. The same folder imported in two places, such as one that two packs from the same repo both include, renders in each, at each one's ref, the way two npm packages can each bring their own version of a dependency. That costs a row or its rules twice, which is simpler to explain than choosing one place or one version. A pack can never include a folder holding itself, which also catches a folder on disk holding `context-packs/` and a path pointing at a folder holding its own pack, either of which would render forever. Origins are compared as written: the same repo spelled two ways gets past the check.
- **The CLI owns `from`, `path` and `ref` in the import packs in `context-packs/`, and people own `when` and the rules.** `add` writes an import pack, `update` rewrites its `ref` and `remove` deletes it, so nobody resolves a commit by hand: the same arrangement as `AGENTS.md`, where the tool writes only the parts it owns. A command writes its import pack before syncing and puts it back if the sync stops, so a pack is never left half installed. An import pack inside a pack from elsewhere is that pack's to change, so the commands leave it alone.
- **Old formats aren't migrated.** In 0.x, a pack or block in an older format stops the sync with the fix to make, and the reference lists the upgrade steps. That's cheaper than code that reads every old format, keeps nothing old around, and never misreads an old file silently.
- **Every doc needs `when:`, and front matter takes no unknown keys.** A doc without a row would be unreachable, and a key the tool doesn't know would otherwise be ignored without a word.
- **Packs are added and removed explicitly.** Installing a Claude Code plugin doesn't add its pack, since that would tie which packs a repo has to one agent's settings, while what the tool writes works for every agent that reads `AGENTS.md`.
- **It's Python behind an npm package.** npx is the familiar way to run a tool like this, and Python needs nothing installed beyond what comes with `git` on macOS. The cost is needing both Node and Python.

# Why context-packs works the way it does

The [README](../../README.md) covers how to use it. This covers the choices that look like mistakes until you know the reason.

- **Packs are copied into each repo, not linked or loaded by a hook.** Cloud sessions and fresh clones see only what's committed, and Codex can't include another file from `AGENTS.md`. A link into a plugin's install folder would differ by machine and break wherever the plugin isn't installed. A hook would have to be set up for each agent, and would load every doc up front instead of only when a row matches.
- **The sync writes whichever instruction file a repo already uses.** Teams differ on `AGENTS.md` versus `CLAUDE.md`, and on how one reaches the other, and that isn't this tool's call. So it syncs the file holding the block, and a repo with files but no block picks one by pasting the two marker lines into it. Only a repo with neither file gets the recommendation: a new `AGENTS.md` with `CLAUDE.md` linked to it. A block in both files stops the sync rather than syncing both, since two copies of the installed packs could drift apart, and a repo that wants both files can have one import the other. It never writes through a symlink, since its target could be anywhere.
- **One folder, `context-packs/`, holds every pack a repo has, and where a pack sits decides where it renders.** The repo's own docs and the import pack of each pack from elsewhere are folders in one tree, so the tree is the only configuration: moving a folder and resyncing moves a pack, with no command and nothing else to keep in step. Earlier versions named each pack's folder in its start marker, so moving a pack meant fixing a marker or running `remove`, and putting a pack inside another took a flag of its own. The folder is fixed, not configurable, since an import pack holding a path already reaches docs kept anywhere else. Making it configurable later needs no change to the format.
- **The folder isn't `docs/agents/`.** Other tools write there, such as the setup skill in mattpocock/skills, and every `.md` file in a pack needs a `when:`, so their files would stop the sync. A folder named for the tool also sits outside any folder a repo might want to import by path, which it couldn't if it were inside one.
- **The sync writes into `context-packs/gen/`, and skips that folder when reading the tree.** It's one known path, so skipping it is simple, and keeping generated files inside the folder they come from keeps the tables' paths short. `gen` can't be a pack's id.
- **`AGENTS.md` holds one block, whose markers hold no settings.** The block holds a header stating the one rule every pack relies on, read a doc when its row matches and change synced content at its source, followed by the rendered tree. The markers only show where the block starts and ends, to people and to the sync, and hold its hash. Inside it, each inlined pack sits between comments naming its id, for people reading the file; the sync never reads them, so they can't drift from anything. The hash covers the block and everything in `context-packs/gen/`, so any edit to synced content stops the next sync, which names the block and the folder rather than one pack; `git diff` shows which.
- **The header names `context-packs/` in its text, not in a marker.** Claude Code strips HTML comments before an agent reads the file, so whatever the agent needs to know has to be in the visible text.
- **A pack's id is its folder under `context-packs/`.** Commands take that path, such as `server/database`, which is unique by construction, so no rule about unique names is needed, and `add` puts a pack anywhere in the tree without a flag for where.
- **Packs are pinned, except a pack in a folder on disk.** A pack pinned to a commit or tag syncs the same for everyone until someone runs `update`. `update` moves a release tag only to a newer release with the same prefix, so a pack pinned to a version never lands on an unreleased commit by accident. A pack in a folder on disk is read from the working tree instead, because a commit can't pin itself: that's what lets a repo holding a pack resync its own `AGENTS.md` in the commit that changes the pack. A folder beside the repo, such as `../agent-config/packs/core`, is read the same way, so an author can try a pack in another repo before pushing it, the way `file:` dependencies work in `package.json`. It syncs only where that folder exists, so it's for trying a pack out, not for a repo that clones, CI and cloud sessions sync. An origin is a folder on disk unless it's a git URL, told apart the way git does it, so `.`, the folders beside it and absolute paths follow one rule, and a pack meant to be pinned is named by its git URL.
- **A pack in a folder on disk is listed where it is, not copied.** A copy would duplicate every doc in the same repo, and editing your own docs would trip the check for synced content edited in place. So its table points at the docs themselves, and a folder beside the repo gets the same treatment, so editing one of its docs needs no resync either. Listing in place is what makes `context-packs/` the home for a repo's own context docs: the table is generated from each doc's `when:` line, so there's no hand-written table to keep in step. Only nested packs' generated indexes go under `context-packs/gen/`.
- **A folder with a `pack.md` is a pack wherever it sits.** `context-packs/` itself is the pack at the top, inlined into `AGENTS.md`, so its `pack.md` takes no front matter. A pack nested inside one gets a row instead, pointing at a generated index that holds its rules and its own table, so a long subtree costs one read only when its row matches, and no one writes an index by hand. A folder without a `pack.md` only groups files: its docs join the nearest pack's table, so arranging files costs no extra read. Any folder with a `pack.md` can also be installed on its own, and it renders the way it would inside its parent: one with a `when` gets a row pointing at its index at `context-packs/gen/<id>/pack.md`, so installing just a language's pack still loads its rules only when they matter. That's its author's suggestion, which the import pack of a repo installing it can overrule.
- **A pack with a `when` is a hop, unless its `when` is `always`.** A hop costs one read when its row matches, while inlining a pack costs context in every session of every repo that installs it, so a nested pack says which it is with a `when`, and gets a row unless that's `always`. A pack you import is also inlined when it has no `when`, the usual case for a pack written to be installed on its own. `always` is a value of `when` rather than a key of its own, so one key decides how every pack loads, a pack you write and an import pack alike, and no two keys can contradict each other. The cost is that no row can read just "always", which no `when` seems to need.
- **A pack installs everything in its folder.** Choosing parts of a pack took a list of picks, a command to change it, and rules for which packs a pick pulls in, all so an author could nest what is really a pack of its own. A part only some repos want goes in a folder beside its parent's, which those repos install with `add`, and a nested pack is only for putting a big subtree's table behind one row.
- **Every pack from elsewhere is installed as an import pack, which decides how it loads.** How a pack renders is decided by its root's front matter, so an import pack is a folder the repo owns whose `pack.md` supplies that front matter, while its content comes from the pack it names. Without a `when`, it follows the root `when` of the pack it names, at the import pack's ref: its author's suggestion holds, and moves with `update`. `when:` replaces it with the repo's own, and `when: always` inlines the pack even when its author gave it a `when`. The author's `when` isn't copied into the import pack, since a copy would be a second source of truth for `update` to keep in step. A folder on disk gets an import pack too, with no `ref`, so every pack is added, moved and overruled the same way. Packs nested inside the imported one still render as their author wrote them, until someone needs to change those too.
- **An import pack is a folder holding a `pack.md`, not any file with `from:` or `path:`.** Every pack being a `pack.md` keeps one rule for finding packs, and a doc's front matter keeps one meaning. The CLI writes the folder, so the extra level costs nothing. The folder holds only `pack.md`, since the repo's own docs beside imported ones would blur which are synced; they can go beside it.
- **`from` names a repo, and `path` a folder in it; without `from`, it's the repo the import pack is in.** That's the synced repo for `context-packs/`, or the repo of the pack from elsewhere holding it, at that pack's ref. One shape covers a pack from git (`from` is its URL), a checkout beside the repo (`from` is its folder), and a folder of the same repo (`path` alone), so switching between trying a pack locally and installing it pinned changes only `from`. Keeping the repo apart from the folder is what lets a pack point at another folder of its own repo and render the same wherever it's installed; folding them into one path would lose which repo a nested path is in. A path is relative to the repo's root rather than to the file, so moving an import pack doesn't break it, and it can't leave its repo, since the repo installing a pack has no way to know what's beside it.
- **A pack from git can only import folders of its own repo.** Importing a pack from git would bring transitive pins and the same pack imported twice at two refs, and a folder on disk would mean something different in every repo installing it. A `path` alone brings neither, since it shares the holder's pin. Lifting this later needs no change to the format.
- **The commands manage only the import packs in `context-packs/`.** An import pack inside a pack from elsewhere is that pack's: one in a pack from git moves with its holder's pin, and one in a folder on disk is edited in that folder, which may not be this repo's to write.
- **The CLI writes import packs, and leaves only `when` and the rules to people.** `add` writes `from`, `path` and `ref`, and `when` if asked, `update` rewrites `ref`, and `remove` deletes the folder, so nobody resolves a commit by hand. It's the same arrangement as `AGENTS.md`: a file people edit, where the tool writes only the parts it owns. A command writes its import pack before syncing and puts it back if the sync stops, so a pack that can't be rendered is never left half installed.
- **Old formats aren't migrated.** A pack or block written for an older version stops the sync as front matter it doesn't know or markers it can't read, says what to use instead, and gets fixed by hand. While there's one consumer, that's cheaper than code that reads every old format, and it keeps nothing old around after it's gone.
- **Every doc needs `when:`, and front matter takes no unknown keys.** A doc without a row would be unreachable, and a key an older version doesn't know would otherwise be ignored without a word. A way to leave a doc out of the table can come when a pack needs one.
- **Packs can't overlap, except the same folder imported in two places.** A pack and a folder inside it from the same origin would sync the inner rules twice, under one pack's heading and as part of another's, so the sync stops. The same folder imported in two places, such as one that two packs from the same repo both include, renders in each, at each one's ref: it's part of each pack as that pack's author shipped it, the way two npm packages can each bring their own version of a dependency. That costs a row or its rules twice, which is simpler to explain than choosing one place or one version for it. A pack can never include a folder holding itself. That also catches a folder on disk that holds `context-packs/` or sits inside it, and a path that points at a folder holding the pack it's in, either of which would otherwise render forever. That's also why a part a repo chooses sits beside its parent's folder, not inside it. Origins are compared as written: the same repo spelled two ways gets past the check.
- **Packs are added and removed explicitly.** Installing a Claude Code plugin doesn't add its pack. That would tie which packs a repo has to one agent's settings, while what the tool writes works for every agent that reads `AGENTS.md`. A trigger for each agent can come later without changing the format.
- **It's Python behind an npm package.** npx is the familiar way to run a tool like this, and Python needs nothing installed beyond what comes with `git` on macOS. The cost is needing both Node and Python; a rewrite in TypeScript would remove the Python requirement if Windows users or contributors need that.

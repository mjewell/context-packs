# Why the review action works the way it does

[Reviewing PRs in CI](../../docs/reference.md#reviewing-prs-in-ci) covers how to use it. This covers the choices that look like mistakes until you know the reason.

- **CI only reports, and every decision happens in the author's local run.** Each finding needs a person to decide it: a deviation can be fixed in the code or in the rule, and `pack-rule` waits for its wording to be approved. A run in CI can't wait for either. So it posts findings, and the author runs `/pack-review <PR>` locally, where the back-and-forth can take as long as it needs, with a checkout to change a pack at its source. Nothing in CI commits or pushes.
- **claude-code-action runs the agent, and our own MCP server is its only way to the PR.** The action installs Claude Code, handles auth, runs only for someone with write access, and restores `.claude/` from the base branch. Its own tools don't fit: its inline comment tool can't reply or resolve, and the comments it fetches for context are filtered only by actor name. `tools.py` gives the agent filtered reads and checked writes instead, and the agent gets no `gh` and no shell beyond git commands that read.
- **The agent writes its threads, and a script writes the summary.** Matching a finding to its thread across pushes, when its lines have moved, takes judgment, and replies read better from the agent. A missed thread costs a comment. The summary holds what the follow-up needs, so `summary.py` writes it from the agent's validated answer in a step after the agent, whatever the agent did on the PR.
- **Reads and writes are cleaned by removing whole classes of hidden content.** A later run reads every comment pack-review writes, and hidden text in a person's comment can carry instructions to the agent, so `sanitize.py` runs both ways. It removes all raw HTML, Markdown image alt text and link titles, and every Unicode format character, rather than matching known tricks, so it needs no list kept current. Code is left as written, since markup in it shows as text. Secrets are redacted by prefix. That matters because claude-code-action keeps its token in the agent's environment and in `.git/config`. The agent can't run a shell, and is denied `Read` on `.git/`, but it's confined only as far as its tools are.
- **The summary lists every finding on its own line, though the threads repeat some of them.** It's the record that stands on its own: whatever the agent did with threads, a person can read every finding there without opening anything.
- **The findings travel as JSON in a `<details>` block in the summary.** The author's run works through exactly what reviewers saw, with only read access to the PR, and a person can open the block to see what it holds. A CI artifact would expire, and reviewing again locally would cost a second review and could find different things. Backticks are written as ```, so nothing in the agent's text can close the code fence. A comment holds at most 65,536 characters, so a summary that doesn't fit stops the run.
- **pack-review's comments are told apart by the token's identity and a marker together.** Other workflows post with the same token, and anyone can type the marker. `viewerDidAuthor` says the token's identity wrote a comment without naming the bot, so it works with any token. The tools add the marker; the sanitizer removes any the agent writes.
- **Only part of the uncovered findings get a thread.** In chat, a weak candidate costs one turn. On a PR, it costs an open thread on every push. So only an uncovered choice that adds a second way beside an existing one gets a comment, and the rest wait in the summary for the local run.
- **`claude_args` is built by `args.py`, with every `'` in JSON written as `'`.** claude-code-action splits `claude_args` the way a shell would, so each value is quoted whole, and a value that's one pair of single quotes reads the same in any shell-style parser.
- **A run's log lists the agent's tool calls, but not what they returned.** Without it, nothing shows whether the agent read the packs or how a thread action went, since claude-code-action keeps the transcript out of the log. Its full output can hold file contents and secrets, so `transcript.py` prints each call's input, and the answer only from the review's own tools, whose text we write.
- **Every list of a PR is read as one page of 100, and more is an error.** Reading more pages adds code no PR has needed, while a review that silently missed some comments would be wrong.
- **claude-code-action is pinned by commit.** The review relies on how it passes `claude_args`, the prompt and the token, and a tag can move.

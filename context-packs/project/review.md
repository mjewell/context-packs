# Why the review action works the way it does

[Reviewing PRs in CI](../../docs/reference.md#reviewing-prs-in-ci) covers how to use it. This covers the choices that look like mistakes until you know the reason.

- **CI only reports, and every decision happens in the author's local run.** Each finding needs a person to decide it: a deviation can be fixed in the code or in the rule, and `pack-rule` waits for its wording to be approved. A run in CI can't wait for either. So it posts findings, and the author runs `/pack-review <PR>` locally, where the back-and-forth can take as long as it needs, with a checkout to change a pack at its source. Nothing in CI commits or pushes.
- **The findings travel in a hidden block in the summary comment.** The author's run works through exactly what reviewers saw, with only read access to the PR. A CI artifact would expire and is fetched differently on each provider, and reviewing again locally would cost a second review and could find different things. The block is base64, since JSON can hold `-->`, which would end the HTML comment early. A comment holds at most 65,536 characters, so a summary that doesn't fit stops the run.
- **The agent holds no token, and reads comments from a file rather than through an MCP.** The diff and the comments are text anyone with access to the PR could have written. An agent with a token could be steered by it, and even a read-only token reads everything its scope covers. `fetch.py` writes only what the agent may see, and filters by role in code, not in a prompt. The agent returns its findings as its answer, validated against `findings.schema.json`, so it needs no tool that writes, and its shell runs only git commands that read.
- **The agent decides what happens to threads, and a script carries it out.** Matching a finding to its thread across pushes, when its lines have moved, takes judgment that rules in code would get wrong. A wrong call costs one extra comment. `post.py` checks only what keeps the PR safe: an action names what it needs, and touches only a thread pack-review started. It checks everything before writing anything, and posts the new threads as one review, so a refused line writes nothing.
- **pack-review's comments are told apart by the token's identity and a marker together.** Other workflows post with the same token, and anyone can type the marker. `viewerDidAuthor` says the token's identity wrote a comment without naming the bot, so it works with any token.
- **Only part of the uncovered findings get a thread.** In chat, a weak candidate costs one turn. On a PR, it costs an open thread on every push. So only an uncovered choice that adds a second way beside an existing one gets a comment, and the rest wait in the block for the local run.
- **Only `fetch.py` and `post.py` know about GitHub.** `gather.py` takes a range of commits and a file of comments and returns findings, so another CI provider needs only its own fetch and post. GitHub is the only one with a user, so it's the only one written.
- **Every list of a PR is read as one page of 100, and more stops the run.** Reading more pages adds code no PR has needed, while a review that silently missed some comments would be wrong.
- **Claude Code is pinned in the action.** The review relies on its flags for tools, plugins and validated output, which can change between versions.

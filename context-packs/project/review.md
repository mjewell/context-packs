# Why the review action works the way it does

[Reviewing PRs in CI](../../docs/reference.md#reviewing-prs-in-ci) covers how to use it. This covers the choices that look like mistakes until you know the reason.

- **CI only reports, and every decision happens in the author's local run.** Each finding needs a person to decide it: a deviation can be fixed in the code or in the rule, and `pack-rule` waits for its wording to be approved. A run in CI can't wait for either. So it posts findings, and the author runs `/pack-review <PR>` locally, where the back-and-forth can take as long as it needs, with a checkout to change a pack at its source. Nothing in CI commits or pushes.
- **Finding and going through are two skills.** `pack-findings` turns a diff into findings, and `pack-review` goes through them with the user. CI runs only `pack-findings`, a local run on a PR CI reviewed runs only `pack-review`, and a local review runs both. `pack-review` loads `pack-findings` with the Skill tool, which can't load a skill that sets `disable-model-invocation`. So `pack-findings` is the one skill without it, and its description names who runs it, so an agent doesn't pick it for other reviews.
- **CI runs the same skill as a local review, and the skill hands every unit to a subagent.** The units split the files, not the packs, so one subagent reads each file whole. The first unit is the instruction file. It holds the rules of every pack inlined in the block. Each other unit is one pack's block from `context-packs docs`. In CI, that list comes from the `docs.txt` the action writes. A nested pack's index is in its pack's block, and it holds that pack's rules. Splitting by pack would leave a subagent to find an inlined pack's rules inside a file other packs share. The agent launches one subagent per unit and reads no doc itself. Then it merges their answers and walks the diff for uncovered choices. A skill that let the agent check a small unit inline read 2 of 15 docs on a 27-line diff. The agent had judged the units weren't worth handing out. With every unit handed out first, local runs read every doc in all 6 tries. Those runs were on that diff and on one with three planted deviations, and they caught all three each time. The prompt each subagent gets is pinned in the skill, so a local review and CI check the same way.
- **Subagents run in the foreground.** `args.py` sets `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS=1` through `--settings`. A subagent running in the background returns at once, so the agent answered before one unit's subagent reported, and the answer left out that unit's findings.
- **The agent gets the docs' names, in `docs.txt`, not their text.** Runs with every doc's text in the prompt never read a doc or spawned a subagent, and found nothing: 5 of 5 at default effort, whether the list of docs was in the prompt or in a file. They treated having the text as having checked it. One run at high effort split the units, but needing high effort for that is a cost every review would pay. Hooks that counted reads from Claude Code's transcripts would rule a skip out, and were tried before that. They tied the review to that transcript format, and a crash in one let the answer through as if every doc was read.
- **The report says which docs the agent read, and lists the ones it skipped.** `report.py` counts each agent's `Read` calls in claude-code-action's transcript with `reads.py`, so a doc counts once one agent read every line of it, and prints who read each doc in the log. It runs after the agent, so it can't change the answer, and unlike the hooks it needs no hook contract or retries. A partial review tells the author more than none, so the summary says which docs no agent read, and `pack-review` says the review is partial before the findings. The report reads Claude Code's transcript format, so another agent would need its own.
- **`context-packs docs` reads the committed tables, not the packs.** Loading the packs fetches each one from git, and in CI a pack's origin can be a private repo the workflow's token can't read.
- **claude-code-action runs the agent, and the agent has no way to the PR.** The action installs Claude Code, handles auth, runs only for someone with write access, and restores `.claude/` from the base branch. The agent's only MCP server is the git server, and it has no `gh`, so nothing it does reaches the PR. It has no shell. It reads files with `Read`, `Glob` and `Grep`, which `--restricted` confines to the checkout and the folder the action writes `docs.txt` to, and it reads the change through the git server. Claude Code checks the paths a shell command reads, but not what it writes: an allowed `git log --format=format:<text> --output=<file>` wrote any text to any file, and git takes any unique prefix of `--output`, so no allow or deny rule on git commands is safe.
- **The agent reads the change through a git server, not a shell.** `git_server.py` is an MCP server over stdio, and each of its tools runs one fixed git command. The agent picks what to read, such as leaving out a lock file's diff, without a way to run git itself. Nothing the agent sends reaches git as an option. A revision reaches git only as the hash `rev-parse --verify --end-of-options` resolves it to. A path must be relative and without `..`, and goes after `--` with `--literal-pathspecs`, so `*` names only a file called `*`. Every diff runs with `--no-ext-diff --no-textconv`, since a PR picks a path's diff driver in `.gitattributes`. Output comes in pages of 1000 lines, so one call can't fill the agent's context. The server is named `git`, since claude-code-action adds its own GitHub servers when an allowed tool's name starts with `mcp__github`.
- **`diff` and `show` start each line the head has with its line number there.** When the agent read the diff as one file, its findings gave line numbers counted in that file, past the end of the files they named. With the number on the line, it copies it instead of counting.
- **The summary lists the diffs no agent read in full, but they don't make the review partial.** `reads.py` counts a path's diff as read once one agent got every page of it from the `diff` tool. Before the agent runs, the action writes `changed.txt` with the server's `changed` command, so the summary counts pages with the same code the agent reads through. Skipping a lock file is often right, so the JSON lists these as `unread_diffs`, and the summary's text doesn't call the review partial, as it does for a skipped doc.
- **An agent reads a PR's threads only through `trust.py`, which filters whose text it gets.** `threads.py` prints pack-review's threads on the one PR it's given, and an agent reads that output, so it needs no tools. A thread counts as pack-review's when its first comment is: the token's identity wrote it, and it ends with the marker. `trust.py` gives a reply's text only when its author's role is write, maintain or admin now, from GitHub's permission API, asked once per author, or when pack-review wrote it. Anyone else's reply comes back as its id and why it's hidden, without the login, which is text its owner chose. Other bots' replies, and replies a maintainer minimized, are hidden too. The text is GitHub's `bodyText`, so GitHub's renderer decides what's hidden, such as HTML comments, and `sanitize.py` then removes invisible characters and redacts secrets. It reads every page. GitHub's lockdown mode doesn't fit: it does nothing on private repos, filters only `issue_read` comments, doesn't strip hidden content, and GitHub calls it best effort.
- **The match job pairs findings with pack-review's threads from the findings' text alone.** `threads.py` reads pack-review's threads through `trust.py`, and `pairing.py` gives the pairing agent only this run's findings and the comment pack-review opened each thread with, which says what it found there. The pairing is an agent so it can judge whether a finding and a thread are about the same issue when their wording differs. No one's reply reaches it, so no comment can change which thread a finding lands in, by mistake or on purpose. A reply saying "fixed" about a fix that missed a spot is the usual case. The agent has no tools and answers against a schema. `pairing.py check` refuses a pair that names no finding, or a thread that isn't pack-review's, or either one twice. The prompt reaches claude-code-action as a step output, under a delimiter `pairing.py` makes sure the text doesn't hold.
- **CI posts a summary, and no comments on the diff.** Threads on the diff need the agent to read the PR's comments and write to it, which takes a filter on whose comments it reads, a check on which threads it may write to, and cleaning both ways. The author's local run goes through every finding anyway, so the summary alone carries them. Threads would also stay open until a person resolves them: GitHub answers `Resource not accessible by integration` when the workflow's token resolves a thread, and the tokens that might be allowed, one with `contents: write` or a GitHub App's, can also push.
- **Scripts write the summary, from the agent's validated answer.** `report.py` runs in the find job after the agent, with the answer claude-code-action checked against `findings.schema.json`, and `summary.py` posts its report in the post job.
- **The review is two jobs, find and post, and only post can write to the PR.** GitHub enforces each job's `permissions`, so the find job's token reads the repo and nothing else, whatever the agent's tools allow. The post job has `pull-requests: write` and runs no agent. A composite action can't start a job or set its permissions, so the review is two actions, `review/find` and `review/post`, and the workflow gives each job its permissions. A reusable workflow could set them itself, but it can't find its own scripts at the ref it was called at, while a composite action has them at `$GITHUB_ACTION_PATH`. The find job hands `report.json` to the post job as an artifact. The transcript stays in the find job, since it can hold file contents. Posts wait for each other rather than cancel, since two at once could each find no summary and add one.
- **The agent's findings lose only invisible characters and secrets before they're posted.** They appear only in the summary's JSON code block, where raw HTML, image syntax and links all show as written, so nothing in them is hidden from a person reading the block. Unicode format characters, such as zero-width spaces and direction overrides, don't show even there, so `sanitize.py` removes every one of them, rather than a list of known ones. Secrets are redacted by prefix. That matters because claude-code-action keeps its token in the agent's environment and in `.git/config`. The agent has no shell, and it's denied `Read` on `.git/`, which also stops `Grep` and `Glob` there, but it's confined only as far as its tools are.
- **The summary shows the agent's text only in its JSON.** A line of the agent's text rendered as Markdown could look different from what the local run reads, such as text in an HTML comment that doesn't render. In a code block, every character shows, so people and the local run see the same text. The summary's own text gives only the counts and the command to run.
- **The findings travel as JSON in a `<details>` block in the summary.** The author's run works through exactly what CI found, with only read access to the PR, and a person can open the block to see what it holds. A CI artifact would expire, and reviewing again locally would cost a second review and could find different things. Backticks are written as `\u0060`, so nothing in the agent's text can close the code fence. A comment holds at most 65,536 characters, so a summary that doesn't fit stops the run.
- **The local run reads the summary through one command `pack-review` gives in full.** Its `--jq` filter runs before the agent sees anything, and prints no comment's text but the summary's, since other comments can hold text written to steer the agent, and a check the agent ran after reading them would come too late. It reads every page, so a summary or a forged block past the first 30 comments isn't missed. It reads the summary's `bodyText`, GitHub's plain-text rendering, which leaves out HTML comments, image alt text, and link titles and URLs. It keeps the text of code, which is how the JSON comes through, and invisible characters, which is why `sanitize.py` removes them before posting.
- **pack-review's comments are told apart by the token's identity and a marker together.** Other workflows post with the same token, and anyone can type the marker. `viewerDidAuthor` says the token's identity wrote a comment without naming the bot, so it works with any token. `summary.py` adds the marker at the end, after the JSON block, so the agent's text can't put it there.
- **`claude_args` is built by `args.py`, with every `'` in JSON written as `\u0027`.** claude-code-action splits `claude_args` the way a shell would, so each value is quoted whole, and a value that's one pair of single quotes reads the same in any shell-style parser.
- **A run's log lists the agent's tool calls, but not what they returned.** Without it, nothing shows whether the agent read the packs, since claude-code-action keeps the transcript out of the log. Its full output can hold file contents and secrets, so `transcript.py` prints each call's input, and only whether its result was an error.
- **A summary is stale when the PR's head or base branch moved, not its base commit.** The base commit is the base branch's tip, so it moves whenever something merges there, while the diff from the merge base stays the same. Retargeting a PR, such as a stacked PR moving onto `main` after its parent merges, changes the diff with the head unchanged, so an edit that changes the base runs the review again. A force push to the base branch can change the diff without either moving, and goes unnoticed.
- **`summary.py` reads the PR's comments as one page of 100, and more is an error.** Reading more pages adds code no PR has needed, while a summary that missed its earlier one would post a second. The local run reads every page, since `gh` does that with one flag.
- **claude-code-action is pinned by commit.** The review relies on how it passes `claude_args`, the prompt and the token, and a tag can move.

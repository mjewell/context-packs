# Why the review action works the way it does

[Reviewing PRs in CI](../../docs/reference.md#reviewing-prs-in-ci) covers how to use it. This covers the choices that look like mistakes until you know the reason.

- **CI only reports, and every decision happens in the author's local run.** Each finding needs a person to decide it: a deviation can be fixed in the code or in the rule, and `pack-rule` waits for its wording to be approved. A run in CI can't wait for either. So it posts findings, and the author runs `/pack-review <PR>` locally, where the back-and-forth can take as long as it needs, with a checkout to change a pack at its source. Nothing in CI commits or pushes.
- **Finding and going through are two skills.** `pack-findings` turns a diff into findings, and `pack-review` goes through them with the user. CI runs `pack-findings` too, as its review job's prompt, and hands the findings to the pairing and post jobs instead of a person. A local run on a PR CI reviewed runs only `pack-review`, and a local review runs both. `pack-review` loads `pack-findings` with the Skill tool, which can't load a skill that sets `disable-model-invocation`. So `pack-findings` is the one skill without it, and its description names who runs it, so an agent doesn't pick it for other reviews.
- **A review runs through the wizard, a command the agent runs one step at a time, locally and in CI.** `context-packs review` does each step's deterministic work, keeps what it learned in a run folder, and prints what to do next, with every command in full. The orchestrator, the agent that ran the skill, starts the subagents it names, in the foreground. A headless session ends when the orchestrator's turn ends, and a subagent in the background ends with it: in one CI run the orchestrator started its finders in the background, and the run ended 14 seconds later with no answers. So `init` and `next` say to start them in the foreground, and CI sets `CLAUDE_CODE_DISABLE_BACKGROUND_TASKS`, which takes `run_in_background` out of the Agent tool. It doesn't decide which units are worth a finder, since the wizard names one for each, and `next` names any whose answer isn't in. The skill grants `Bash(npx context-packs@<version> review:*)` in its `allowed-tools`, but only for the turn that invoked it, and a notification that a subagent finished starts a new turn. The finders start in that turn, and in smoke runs on Claude Code 2.1.327 their calls stayed allowed after it ended. The orchestrator's later calls, such as `next` once the finders report, aren't covered: an interactive session asks about them, as it asks about any command, and a headless run, such as CI's, allows the wizard's command at startup with `--allowedTools`. So every step an agent takes goes through that one command, and no agent reads or writes the run folder: an agent writes its answer with its tool for writing files to the path its brief names, in an answers folder beside the run folder, and runs `submit N`, and the briefs print their schemas. Answers don't go in the agent's scratchpad, since a scratchpad exists only for some accounts: a CI review's finders had none, so none of their answers could be written. The answer can't go in the command, such as in a heredoc: Claude Code refuses a command with a brace before a quote, which every JSON object starts with. In a smoke run every heredoc answer was refused. The briefs say to run each command exactly as printed, since agents that wrapped one in a shell variable or a `cd` lost turns to Claude Code refusing it. The wizard takes only the options it names, spelled out, since an allowed Bash prefix passes any arguments after it. It reads the change through fixed git commands in `change.py`, and checks a diff's path against the paths the change touches.
- **Each unit gets its own finder, and the wizard names them all.** The units split the files, not the packs, so one finder reads each file whole. The first unit is the instruction file. It holds the pack rules of every pack inlined in the block. Each other unit is the docs one pack's table points at, as `context-packs docs` groups them. One more finder, the uncovered finder, has no unit. It reads the whole diff for choices no rule covers, and searches every unit's docs for a rule that settles each one. It runs alongside the units' finders, so the merge doesn't read the diff for them after. A nested pack's index is a doc in its parent's unit, and it holds that pack's pack rules. Splitting by pack would leave a finder to find the pack rules of an inlined pack inside a file other packs share. The wizard names one subagent per unit, and the orchestrator starts them all at once and reads no doc itself. `next` names any finder whose answer isn't in, and the merge can't start until every one is, so no agent decides whether a unit is worth checking: an agent left to decide skipped units on small diffs. A unit's finder gets the prompt in `unit-prompt.md`, the uncovered finder gets `uncovered-prompt.md`, and the merging agent gets `merge-prompt.md`. The wizard gives each agent its file, so a local review and CI check the same way. A finder reports a spot only when a careful reader would agree it breaks the rule. A rule that calls for judgment, such as Plain Prose, can always be applied more strictly, and each run then finds a new problem in the same lines. The wizard fills each one and adds what every agent needs beyond it: the commands that read its docs and the change, to copy line numbers from the numbered diff, and how to hand in its answer. What it adds is whole sentences, so each kind of finder's addition stands on its own. The three files live in the skill's folder. A prompt only CI uses, such as the pairing and commentary agents', lives in the script that fills it, since no local run reads it.
- **A finder gets its docs' names, not their text.** Runs with every doc's text in the prompt never read a doc or spawned a subagent, and found nothing: 5 of 5 at default effort, whether the list of docs was in the prompt or in a file. They treated having the text as having checked it. One run at high effort split the units, but needing high effort for that is a cost every review would pay. Hooks that counted reads from Claude Code's transcripts would rule a skip out, and were tried before that. They tied the review to that transcript format, and a crash in one let the answer through as if every doc was read.
- **The review checks that every doc was read, but not which diffs were.** The wizard prints each doc through `doc` and refuses a unit's answer until it printed every one, so the check needs no transcript. Checking reads from Claude Code's transcript would have meant parsing it in every job, since a transcript can't leave its job. Skipping a diff, such as a lock file's, is often right. A run's log lists every tool call, so a skip can be checked by hand.
- **`context-packs docs` reads the committed tables, not the packs.** Loading the packs fetches each one from git, and in CI a pack's origin can be a private repo the workflow's token can't read.
- **claude-code-action runs the agent, and the agent has no way to the PR.** The action installs Claude Code, handles auth, runs only for someone with write access, and restores `.claude/` from the base branch. The agent has no MCP server and no `gh`, so nothing it does reaches the PR. It loads `pack-findings` from the review's own checkout with `--plugin-dir`. Its shell runs only the commands the skill runs: the wizard's `review` and `docs`, `git rev-parse` and `git status`, each allowed as a command prefix. The prompt asks for the skill's `checkout` CLI, `python3 <checkout>/src/cli.py`, so the wizard is the pinned commit's, as `report.py`, pairing and post are. With the npm release the skill pins, a run at a commit between releases would pair one version's wizard with another's report, and this repo's own PRs would be reviewed by the previous release's wizard. The skill builds the path from its own folder, without `..`, so the agent's commands match the allow rule, which names the same absolute path. It reads files with `Read`, `Glob` and `Grep`, which `--restricted` confines to the checkout, and writes only in the answers folder, which the job makes before the agent starts. On Claude Code 2.1.318, a headless run wrote outside its working directory only with both `--add-dir` and an `Edit(//<folder>/**)` rule: either alone was refused. Claude Code checks the paths a shell command reads, but not what it writes: an allowed `git log --format=format:<text> --output=<file>` wrote any text to any file, and git takes any unique prefix of `--output`. So the only git commands allowed are `rev-parse` and `status`, which have no option that writes a file. On Claude Code 2.1.327, an allowed prefix refused redirects, `$(…)`, backticks, `<(…)`, env prefixes, `&&`, `;`, pipes, `&` and a newline after it, but let options through, so the wizard takes only the options it names.
- **The agent reads the change through the wizard, not git.** `change.py` runs one fixed git command for each of the wizard's `files`, `diff` and `log`. The agent picks what to read, such as leaving out a lock file's diff, without running git itself. It sends only a path and a page number, never a revision. A path must be one the change touches, and goes after `--` with `--literal-pathspecs`, so `*` names only a file called `*`. Every diff runs with `--no-ext-diff --no-textconv`, since a PR picks a path's diff driver in `.gitattributes`. Output comes in pages of 1000 lines, so one call can't fill the agent's context. `change.py shown`, run by the review job and not by an agent, gives the report the lines each diff shows.
- **`diff` starts each line the head has with its line number there.** When the agent read the diff as one file, its findings gave line numbers counted in that file, past the end of the files they named. With the number on the line, it copies it instead of counting.
- **An agent reads a PR's threads only through `trust.py`, which filters whose text it gets.** `threads.py` prints pack-review's threads on the one PR it's given, and an agent reads that output, so it needs no tools. A thread counts as pack-review's when its first comment is: the token's identity wrote it, and it ends with the marker. `trust.py` gives a reply's text only when its author's role is write, maintain or admin now, from GitHub's permission API, asked once per author, or when pack-review wrote it. Anyone else's reply comes back as its id and why it's hidden, without the login, which is text its owner chose. Other bots' replies are hidden too. A minimized comment isn't hidden, since only pack-review and people who can write get past the filter, and the same people can push to the PR. It comes with GitHub's reason, such as outdated, for the commentary agent to weigh. The pairing agent never sees it, so minimizing a thread's opening comment doesn't unpair the thread, which would open a new thread on the next push. The text is GitHub's `bodyText`, so GitHub's renderer decides what's hidden, such as HTML comments, and `sanitize.py` then removes invisible characters and redacts secrets. It reads every page. GitHub's lockdown mode doesn't fit: it does nothing on private repos, filters only `issue_read` comments, doesn't strip hidden content, and GitHub calls it best effort.
- **The pairing job pairs findings with pack-review's threads from text pack-review wrote.** `threads.py` reads pack-review's threads through `trust.py`, and `pairing.py` gives the pairing agent only this run's findings and the comment pack-review opened each thread with, which says what it found there. The pairing is an agent so it can judge whether a finding and a thread are about the same issue when their wording differs. No one's reply reaches it, so no comment can change which thread a finding lands in, by mistake or on purpose. A reply saying "fixed" about a fix that missed a spot is the usual case. The job checks out the PR though its agents read no files, since claude-code-action restores `.claude` and the instruction files from the base branch with git, and fails outside a checkout. The agent's only tool is `StructuredOutput`, which Claude Code returns a `--json-schema` answer through: `--tools ''` removes that one too, and the agent then answers in text, which fails the step. `pairing.py pair-check` refuses a pair that names no finding, or a thread that isn't pack-review's, or either one twice.
- **Commentary comes from a second agent call, after the pairs are fixed.** It gets every paired finding with its thread as `trust.py` filters it, every run. Its own comments are labelled as its own, and people's replies after its last comment are marked as new, so it can tell what it already said: labelled by the bot's login instead, it relayed the same reply on every push. It's told that most findings need no commentary, and to write it only when a new reply, or the review finding the issue again, gives the author a reason to act that it hasn't already given. It sees every paired thread, not only ones with a new reply, so an author who pushed a fix without saying so still hears when it didn't work. Its answer can only add text next to a paired finding: `pairing.py comment-check` refuses commentary on an unpaired finding, two entries for one, or an empty one, and cleans the text like the findings.
- **The merging agent answers with groups, and a script builds the findings.** The wizard numbers every finder's finding in `sources.json`. The agent answers with groups, each the ids of the findings that make one finding, with its kind, headline and take. `report.py`'s checks, through the wizard's `submit-groups`, refuse groups that leave out a finding, name one twice, or name one no finder reported. It then builds each finding's rules, spots, signs and exemplars from its group's findings, so a merge can't drop what a finder found. A spot that two findings disagree on deviates, since it goes against at least one rule.
- **One choice is one finding, however many rules it breaks.** When rules from different units flag the same choice at the same spots, the merge step writes one finding that quotes each of them. Kept apart, one import that two docs forbid opened two threads on the same line, and the second read as a new issue.
- **The review can't see a conflict between two units' rules.** A finder reports only the rules a spot breaks. So when code follows one unit's rule and breaks another's, the merge sees a deviation. Finding the opposing rule at the merge would mean the agent writing rule text again, which the groups exist to prevent. It's left for a change that has finders report every rule that applies at a spot.
- **CI opens a thread for each new finding, and replies in it only when there's something to say.** A finding the pairing job didn't pair gets a thread on its anchor: `report.py` picks the first deviating spot the diff shows, or else the first spot it shows, since a review comment needs a line in the diff. A finding with no spot in the diff is in the summary only. The thread opens with the finding written for people: its headline, the rules it quotes, marking any whose doc wasn't routed, the other spots it was found at, any signs it's deliberate, how the code makes an uncovered choice now, and the take. Each part shows only when the finding has it, so the author can decide from the thread alone. The next run's pairing agent reads that same text, so the thread holds no JSON, and only the summary keeps findings as JSON, for the local run. A paired finding gets a reply only with commentary, or when its thread was resolved, so re-running a review stays quiet. A thread with no finding gets nothing, since the review doesn't say whether a thread is resolved: the author decides that, and resolves it. The workflow's token can't resolve a thread: GitHub answers `Resource not accessible by integration`, and the tokens that might be allowed, one with `contents: write` or a GitHub App's, can also push. So a resolved thread hears its finding is still there from a reply, once: `post.py` doesn't say it again while that reply is the thread's last comment.
- **`post.py` writes only to pack-review's threads on this PR, and never leaves a review pending.** It reads the threads again itself through `trust.py`, rather than trusting the pairing job's list, and stops if a pair names any other thread. It opens the new threads in one review, submitted as a comment as it's created, and posts each reply on its own. A reply can join a review only while the review is pending. A pending review left by a failed or cancelled run would block the next, since GitHub allows one per user on a PR. So replies notify separately, and they're rare. It plans every write, the review and the summary, and checks the plan before the first one. A PR that moved on, a pair naming another thread, a summary too long for a comment or a second summary each stop it with nothing written. A network error partway through can still leave the threads without their summary, and the local run then finds a summary for an older head, or none.
- **Text in threads renders as Markdown, with mentions and HTML escaped.** A thread's opening finding and any commentary read like a person wrote them. Each comment opens with its kind and commit as code spans, such as `deviation` `abc1234`, which read as tags and need no image from another site. The findings come from the review agent, and the commentary from the replies of people who can write to the repo. `finding_comment.py` puts a word joiner, which doesn't show, after each `@` that a login character follows, so no one is notified. GitHub links a mention only when the login comes right after the `@`, so this holds whatever Markdown is around it. Backticks around the mention wouldn't hold, since the agent's own backticks can pair with them and leave it outside a code span. The next run's `trust.py` removes the joiner with the other invisible characters. It also escapes `<`, so no HTML comment or tag can hide text. Links and images still render. The summary keeps the agent's text in a JSON code block, since the local run parses it there.
- **Scripts write the summary, from the findings the wizard built.** `report.py` runs in the review job after the agent. It reads the one run folder with findings from the `TMPDIR` the job gave the agent, refuses findings for another head, and adds each finding's anchor. `post.py` posts the summary `summary.py` renders from it, in the post job. A review that didn't reach its findings fails the job.
- **The review is four jobs, and only post can write to the PR.** GitHub enforces each job's `permissions`: review reads the repo and nothing else, pr also reads the PR's head and base and runs no agent, pairing reads pack-review's threads, and post has `pull-requests: write` and runs no agent. A composite action can't start a job or set its permissions, so the jobs live in a reusable workflow, `.github/workflows/review.yml`, and each runs its own action under `review/`, or a step of its own. A repo calls the workflow with one job, and grants the most any job gets. Each job checks out this repo at `job.workflow_sha`, the commit the caller pinned, and runs the actions from there, since a `uses:` line can't take an expression to name a commit. That checkout goes in `.pack-review` after the PR's own, since checking out the PR cleans the workspace. `job.workflow_sha` isn't on GitHub Enterprise Server, so the review needs GitHub.com. The jobs hand their results on as artifacts.
- **A newer run cancels the one before it, and each run reviews the PR as it is when it starts.** The workflow has one concurrency group per PR. GitHub doesn't promise to queue runs in the order of their events, so the run that's left can be an older one. So the pr job reads the PR's head and base from GitHub, not from the event, and every later job reviews those commits. The run that's left was queued after every run it cancelled, so after the pushes that started them, and its pr job starts later still: it reviews the newest head. A run that won't review, such as one for a title edit, gets a group of its own, keyed by its run id, so the group's name repeats the pr job's condition. In the shared group it would cancel a review waiting there: GitHub cancels a run waiting in a group when another joins, and a review waits for a few seconds while the run before it is cancelled. A run cancelled during post leaves only posted comments, since post never leaves a review pending. A reusable workflow's top-level `concurrency` takes effect, though GitHub's docs don't say so. If that stops, every run finishes: the reviews are still right, and each push pays for one. Posts wait for each other rather than cancel, since two at once could each find no summary and add one.
- **The agent's findings lose only invisible characters and secrets before they're posted.** In the summary's JSON code block, raw HTML, image syntax and links all show as written, so nothing in them is hidden from a person reading the block. In threads and the summary's list, the text renders, escaped. Unicode format characters, such as zero-width spaces and direction overrides, don't show even there, so `sanitize.py` removes every one of them, rather than a list of known ones. Secrets are redacted by prefix. That matters because claude-code-action keeps its token in the agent's environment and in `.git/config`. The agent's shell runs only the commands it's allowed, and it's denied `Read` on `.git/`, which also stops `Grep` and `Glob` there, but it's confined only as far as its tools are.
- **The summary lists each finding's headline for people, escaped as thread text is.** A finding with no line in the diff gets no thread, so without the list it would show only in the JSON. Each line gives the kind, the headline and the thread's `path:line`, or says the diff shows no line for it. The headline goes through `escaped()`, so it can't notify anyone, and no HTML comment or tag can hide part of it. Links in it still render, as in threads. The local run reads only the JSON, and the rest of the agent's text, such as the take, appears only there. Each headline is kept on one line and followed by more text, since the local run takes the JSON from after the first "Findings for pack-review" and a line break.
- **The findings travel as JSON in a `<details>` block in the summary.** The author's run works through exactly what CI found, with only read access to the PR, and a person can open the block to see what it holds. A CI artifact would expire, and reviewing again locally would cost a second review and could find different things. Backticks are written as `\u0060`, so nothing in the agent's text can close the code fence. `<` is written as `\u003c`, so the block's title appears only once, which the local run checks. A comment holds at most 65,536 characters, so a summary that doesn't fit stops the run.
- **The local run reads the summary through one command `pack-review` gives in full.** Its `--jq` filter runs before the agent sees anything, and prints no comment's text but the summary's, since other comments can hold text written to steer the agent, and a check the agent ran after reading them would come too late. It reads every page, so a summary or a forged block past the first 30 comments isn't missed. It reads the summary's `bodyText`, GitHub's plain-text rendering, which leaves out HTML comments, image alt text, and link titles and URLs. It keeps the text of code, which is how the JSON comes through, and invisible characters, which is why `sanitize.py` removes them before posting.
- **pack-review's comments are told apart by the token's identity and a marker together.** Other workflows post with the same token, and anyone can type the marker. `viewerDidAuthor` says the token's identity wrote a comment without naming the bot, so it works with any token. `summary.py` adds the marker at the end, after the JSON block, so the agent's text can't put it there.
- **`claude_args` is built by `args.py`, with every `'` in JSON written as `\u0027`.** claude-code-action splits `claude_args` the way a shell would, so each value is quoted whole, and a value that's one pair of single quotes reads the same in any shell-style parser.
- **A step output the PR can shape goes through `args.output()`.** A prompt holds text from the PR, and a line in it could set another output. `args.output()` writes the value under a delimiter made for it, which the value can't hold. A value the PR can't shape, such as a commit, a branch name or a folder the step made, holds no line break, so a step can echo it.
- **A run's log lists the agent's tool calls, but not what they returned.** Without it, nothing shows whether the agent read the packs, since claude-code-action keeps the transcript out of the log. Its full output can hold file contents and secrets, so `transcript.py` prints each call's input, and only whether its result was an error.
- **A summary is stale when the PR's head or base branch moved, not its base commit.** The base commit is the base branch's tip, so it moves whenever something merges there, while the diff from the merge base stays the same. Retargeting a PR, such as a stacked PR moving onto `main` after its parent merges, changes the diff with the head unchanged, so an edit that changes the base runs the review again. A force push to the base branch can change the diff without either moving, and goes unnoticed.
- **`post.py` reads the PR's comments as one page of 100, and more is an error.** Reading more pages adds code no PR has needed, while a summary that missed its earlier one would post a second. The local run reads every page, since `gh` does that with one flag.
- **claude-code-action is pinned by commit.** The review relies on how it passes `claude_args`, the prompt and the token, and a tag can move.
